# Stern-To review and optimisation

23 November 2026

## Release status

The code review and optimisation pass is implemented on `improve/game-review-2026-11-23`. It is ready for review, with a real WebGL 2 desktop and phone play-test still required before merging into `main` and publishing.

The work incorporates `main` at `32f41e484aa30c73c9928425a8a801bf171a9862`, including the change that moves exhaust outlets to the hull sides. The three vessels, four harbour selections, existing handling coefficients, mission route and visual identity are retained.

## Main findings and changes

| Area | Finding | Implemented change |
| --- | --- | --- |
| Simulation timing | Player input, traffic and visual work did not all follow the same clock. A stalled frame could create excessive catch-up work. | Input, traffic, mission timing and vessel physics use a fixed 60 Hz step. Catch-up is capped at six steps, with interpolation for drawing. |
| Restart state | Weather altered during a mission, traffic positions and transient effects could survive a restart. | Restart restores the selected weather, initial traffic state, timers, control holds, wakes, foam, smoke, ropes, chains and vessel animation state. |
| Mission flow | Passage completion used a wall-clock callback that could fire after reset or while paused. Keyboard restart could ignore the selected mission stop. | The passage countdown belongs to simulation state. Restart cancels it; pause freezes it. R restarts through the same flow as the Start button. |
| Collision response | Moving-vessel contact did not consistently account for the other vessel's velocity. Contained collision shapes could produce an incorrect separation distance. | Contact response uses relative velocity and corrected separating-axis overlap. |
| Anchors and scoring | A deployed anchor could qualify without actually holding. Interrupted repairs could lose the damage already repaired from scoring history. | Anchorage completion requires a set, holding anchor. Repaired damage is accumulated as work happens. |
| Concurrent controls | Releasing one pointer or key could cancel a different held input. Focus loss could leave momentary controls active. | Inputs have separate ownership; release restores any other active hold. Blur, pause, menu and page lifecycle events clear transient controls. Latched engine settings remain deliberate. |
| Keyboard and dialogs | Global shortcuts could interfere with focused sliders, native buttons and Help. Pause state and focus could become inconsistent. | Focused sliders handle their own keys; native button actions remain intact. Dialogs trap focus, make the background inert and restore focus appropriately. Toggle keys ignore repeats. |
| Animation scheduling | Focus-triggered invalidation could schedule a second animation loop. Menus and paused scenes kept doing unnecessary work. | One guarded animation loop serves the game. Idle scenes stop scheduling frames after settling and redraw on interaction or layout changes. |
| Layout and HUD | Layout measurements and text updates were repeated during drawing. Camera projection could use a stale matrix. | Layout is measured when invalidated, HUD updates are limited to 15 Hz, unchanged control text is skipped, and camera matrices are updated before overlay projection. |
| Graphics memory | Rebuilding boats or harbours left owned GPU resources without disposal. | Outgoing geometry, materials and instanced meshes are disposed. Shared cached resources remain alive for later use. |
| Dynamic graphics | Some particle and line buffers uploaded unused capacity. Frozen scenes still performed effect work. | Dynamic attributes upload active ranges; zero-time foam passes and effect updates are skipped. Wave settings are cached. |
| Drawing resolution | High pixel density can multiply the drawing-buffer cost on phones and large screens. | Pixel ratio is capped at 2 and the drawing buffer at 4.2 million pixels. Sustained frame timing adjusts shader quality and resolution with separate degradation and recovery delays. |
| Startup and graphics recovery | Failed engine loading or graphics initialisation could leave an unusable screen. Context loss could discard a run. | A loading state stays visible until the first successful frame. Failures show a usable retry message. Context recovery preserves the simulation and leaves play paused. |
| Dependencies | The game used Three.js r128 from a CDN. | Three.js r187 is pinned and served locally, with current colour-space and lighting APIs, an integrity manifest and the MIT licence. |
| Counter and wake lock | Preview runs could affect the public play counter, and wake-lock requests could overlap. | The counter runs only at the exact production origin/path, has a timeout and ignores stale values. Wake-lock requests are deduplicated and released when play pauses or becomes hidden. |
| Maintenance | One HTML file combined page structure, CSS, loading, rendering and simulation without a repeatable verification workflow. | Structure, styling, bootstrap and runtime utilities now have separate files. A test suite, lockfile, reproducible vendor script and GitHub Actions checks accompany the game. |

## Technical decisions

### Keep deployment simple

The game remains a static website. GitHub Pages serves the committed files directly; deployment needs no framework, application server or package installation. Development dependencies are used only to test the game and regenerate the pinned engine bundle.

Most simulation and scene code stays in `src/game.js`. Splitting every existing function into a new abstraction would add review risk without a demonstrated runtime benefit. The file now has a clear module entry point, while reusable timing and quality policies are isolated in `src/runtime.js`.

### Upgrade the engine deliberately

Three.js r187 is the current official release checked for this review. The migration includes `outputColorSpace`, current shader colour-space chunks and updated lighting behaviour. Ambient and directional intensity changes account for the lighting migration; the party point light is separately calibrated.

The upgrade requires WebGL 2. Very old devices or browsers with graphics acceleration disabled may not be able to play. They now receive a readable error rather than a blank canvas. The resulting water, glass, daylight and party lighting still need an actual GPU visual check.

The committed engine bundle contains 51 exported symbols and is 588,197 bytes before HTTP compression. This is an observed artifact size, not a claim that the whole game downloads faster than the previous version.

### Optimise bounded work before changing the look

The changes reduce avoidable drawing, repeated layout reads, unused buffer uploads and leaked resources. Adaptive quality responds to sustained frame timing rather than a single slow frame. Long background gaps are excluded from quality measurements.

The existing 384-by-384 sea grid is retained. Reducing its 294,912 triangles without GPU profiling and a visual comparison could change the wave silhouette and reflection quality. A measured mobile profile is the appropriate next input for that decision.

## Verification

The final local verification includes a clean dependency installation, JavaScript syntax checks, the complete automated suite and reproduction of the committed engine bundle.

The suite contains **51 passing tests**, covering:

- Timing at 30, 60, 120 and 144 Hz, irregular frames, long stalls, pixel budgets and quality recovery.
- Reset behaviour, traffic, collision containment, moving contacts, anchor holding, repair scoring and passage cancellation.
- Focused keyboard input, concurrent pointers, native button behaviour, dialog focus, repeated keys and mission-start restart.
- Counter isolation, request timeout, stale responses and wake-lock ownership.
- Startup success, module-load failure, unsupported graphics and recovery messages.
- All 12 vessel/harbour combinations building, advancing simulation and resetting with actual Three.js objects.
- Scene rebuilding, resource disposal, shared-resource preservation, active upload ranges, pause interpolation, camera matrices and the single animation-loop invariant.
- Local asset paths, bundle checksum and required engine exports.

The integration harness executes the complete production game in jsdom with actual Three.js geometry, materials and matrix classes. It substitutes DOM measurements, a clock and a renderer that records scene/resource behaviour. These checks exercise application logic; they do not perform WebGL rendering or compute CSS layout.

After each of two complete rebuild cycles through all vessels and harbours, returning to the same superyacht/fuel scene produced the same tracked resource counts: 132 geometries, 98 materials, two instanced meshes and two observed textures. Owned resources emitted disposal events and cached shared resources were not disposed. This verifies JavaScript ownership and disposal behaviour, not measured GPU memory consumption.

### Browser verification limitation

The available test browser could not create a WebGL context for the existing live game, and its security policy blocked the local preview. Consequently, no actual device FPS improvement, GPU shader compilation result or finished mobile layout is claimed. The review branch must remain unpublished until the following checks pass in a working WebGL 2 browser.
